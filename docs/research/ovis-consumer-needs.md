# Ovis consumer needs from an agent-native terminal runtime

This spec lists what the Ovis client (devswha/ovis 0.4.21, a Bun + React client for herdr) needs from an agent-native terminal runtime. It is synthesized from five explorer reports. Citations are copied verbatim from the reports, as `ovis/<path>:<line>`; the backticks that wrap citations in needs-3 are dropped, and the path and line are unchanged.

## Summary: what Ovis needs that herdr does not give it

1. A persistent, multiplexed RPC and event connection. herdr closes ordinary RPC connections after one response and ignores a second `events.subscribe` on an open connection.
2. Event streams with revisions or cursors, explicit loss and close reasons, and a defined order relative to snapshots. Ovis currently resyncs from snapshots after a gap.
3. Stable identity for the runtime instance, pane, terminal, session and process across handoffs, moves, restarts and PID or pane-ID reuse.
4. A terminal attach that returns structured results: ready, refused, slot held, takeover and handoff. Ovis currently parses attach output text and control sequences to work these out.
5. Per-subscriber backpressure, bounded replay with terminal modes for late joiners, an explicit repaint, grid and geometry signals, and the same attach support on every platform, including Windows. Windows currently falls back to polling `pane.read`.
6. Ordered, acknowledged input with an atomic check-and-send against a verified pane and session target, plus terminal mode state such as bracketed paste.
7. Prompts and approvals as structured, versioned requests with choices, liveness and a typed answer operation. Ovis currently parses them from the screen per provider.
8. An agent turn-state signal (working, idle, blocked, done, background) and typed conversation records with stable IDs, cursors, branches and metadata. Ovis currently reads agent-specific transcripts or falls back to scrollback.
9. First-class remote machines, worktrees, plugins and updates. That means authenticated, scoped endpoints, capability and version negotiation, durable plugin run IDs, and safe staged installs.
10. Enforced observe and interact roles, user-authorized takeover, and caller authority rechecks before a write. Ovis currently enforces these on its own side of the herdr socket.

## Inferred-from-screen behaviors

These are behaviors Ovis currently derives from terminal text, control sequences or transcripts because herdr gives it no structured signal. Behaviors reported by more than one explorer are merged into one item, which lists every citation.

- **Attach outcome.** Ovis decides whether an attach succeeded, was refused, or found the slot held by matching attach output, filtering setup and teardown control sequences, and reading the last-line error text. It treats the first printable bytes as the attach-ready signal, and it detects takeover by matching herdr's final diagnostic after teardown. Citations: `ovis/server/core/terminal-process.ts:24`, `ovis/server/core/terminal-process.ts:36`, `ovis/server/core/terminal-process.ts:49`, `ovis/server/core/terminal-process.ts:53`, `ovis/server/core/terminal-process.ts:57`, `ovis/server/attach-output.ts:1`.
- **Resize redraw.** Ovis infers that a resize redraw is a full screen by parsing synchronized-update ANSI, cursor row moves and plain ASCII row widths. Citation: `ovis/server/core/terminal-process.ts:112`.
- **Terminal modes for late joiners.** Ovis rebuilds terminal mode state from ANSI mode-setting sequences that have fallen out of the replay tail. Citation: `ovis/server/output-window.ts:145`.
- **Mirror mode.** The mirror-only terminal polls `pane.read` and repaints ANSI text instead of receiving an output stream. It also polls pane dimensions, because herdr does not announce layout changes on an event Ovis listens to. Citations: `ovis/server/mirror.ts:3`, `ovis/server/mirror.ts:29`.
- **Prompt and dialog detection.** Provider-specific parsers read the live screen to detect question, approval, model, effort and submit dialogs from Claude, Pi, Codex, OpenCode and OmO, with a generic fallback. Prompt cards can be built from menus visible on screen. Citations: `ovis/server/prompt.ts:23`, `ovis/server/dialogs/live.ts:1`, `ovis/shared/protocol.ts:308`, `ovis/docs/guide.md:174`, `ovis/docs/guide.md:313`.
- **Prompt liveness.** Ovis judges whether a prompt is still active by its position near the screen tail and by matching footer or hint text. Citation: `ovis/server/dialogs/live.ts:88`.
- **Prompt answers.** Ovis works out answer navigation and keystrokes from the parsed dialog content and key hints, not from a shared structured prompt object. Citation: `ovis/server/dialogs/live.ts:2`.
- **OmO questions and pending input.** Ovis recognizes question hints, input-box glyphs, footer layout and task-widget rows on screen. Citation: `ovis/server/dialogs/live.ts:19`.
- **Claude input box.** Ovis reads draft text, suggested prompts and restored cancelled messages from the visible input area, using ANSI dim and inverse attributes and cursor styling. Citations: `ovis/server/prompt.ts:32`, `ovis/server/claude-input.ts:43`, `ovis/server/claude-input.ts:349`, `ovis/shared/protocol.ts:309`.
- **Claude rewind dialog.** Ovis detects it from the screen panel and the absence of the input box. Citation: `ovis/server/claude-input.ts:234`.
- **Password, SSH passphrase and PIN prompts.** Ovis spots these on the last visible line, derives a password field from the text, and checks a fresh screen read before typing a secret. Citations: `ovis/docs/guide.md:250`, `ovis/server/core/input.ts:285`.
- **Command Code permission prompts.** Ovis reads these from the screen, not from the session file. Citation: `ovis/docs/guide.md:233`.
- **Agent status from the screen.** Ovis detects agent status and some agent-specific prompt conditions from screen text and status lines. Citation: `ovis/server/pane-routes.ts:263`.
- **Completion state.** When no native integration identifies the agent, Ovis derives finish state from screen and process evidence. Citation: `ovis/server/completion.ts:11`.
- **Turn status from transcripts.** Ovis takes GJC turn status from the transcript, because herdr's status can reflect provider-child work rather than the parent turn. It takes OmO status from OmO's own session transcript. Citations: `ovis/server/gjc-status.ts:2`, `ovis/server/omo-status.ts:77`.
- **Conversation from transcripts.** Turns, session history, titles and first prompts are parsed from agent-specific transcript records. Citations: `ovis/shared/protocol.ts:198`, `ovis/server/session-history.ts:489`.
- **Scrollback fallback.** When no native transcript can be identified or read (Devin included, when its session identity is missing or ambiguous), Ovis shows recent terminal output as a labelled fallback. Citations: `ovis/shared/protocol.ts:223`, `ovis/docs/chat-mode-audit.md:115`, `ovis/docs/guide.md:167`, `ovis/docs/guide.md:174`, `ovis/docs/guide.md:241`.
- **Agent and session identification.** Ovis infers agent identity from process trees. When native Codex session identity is absent, it matches recent pane text against candidate transcripts and requires a unique, substantial match. Citations: `ovis/server/conversation.ts:2`, `ovis/docs/chat-mode-audit.md:51`.
- **Command outcome.** Ovis ties a sent command to its outcome by watching screen echoes, terminal rows and parsed dialogs. Citation: `ovis/server/outcome.ts:1`.
- **Plugin-created panes.** Ovis identifies the pane a plugin opened from the plugin command's printed output, not from an event linking the invocation to the pane. Citation: `ovis/shared/plugins.ts:43`.

## Open questions for the runtime design

Merged and deduplicated from the open questions in all five reports.

**Connection and protocol**
- Can the runtime offer one persistent, multiplexed RPC and event connection, or should Ovis keep assuming one request per connection?
- What are the maximum response and event sizes, the request deadlines, and the latency targets for snapshots, status events, workspace mutations, transcript reads and terminal streams?
- How do clients negotiate capabilities and versions per machine, covering direct attach, screen mirroring, PTY-host constraints and other optional features?

**Events and snapshots**
- Can events carry sequence numbers or cursors so a reconnecting client can resume? Or must every gap trigger a full snapshot resync, in which case snapshots need a revision number so clients can reconcile without timing-based inference?
- Can a subscription change its filter set in place and report explicit loss and close reasons? Are events guaranteed to be ordered relative to snapshots and transcript revisions?
- What are the delivery guarantees, backpressure behavior and output-buffer bounds for slow observers, stalled clients and remote clients? Can backpressure be applied per subscriber without pausing a shared producer?

**Identity and lifecycle**
- Where are the stable identity boundaries: runtime boot, terminal server, session, pane lifetime and pane-ID reuse? Do pane and session identities survive a server handoff, and are terminal-generation changes reported explicitly?
- How should state behave across a remote disconnect, a runtime restart, a session restart and a host reboot?
- What are the PTY-host lifecycle guarantees on each supported platform: process-group cleanup, child exit codes, resize, and same-size SIGWINCH-equivalent behavior?

**Terminal attach**
- Can attach acquisition, held-slot conflicts, readiness and takeover come back as structured RPC results instead of terminal text?
- Is attach multi-client by design, or does the runtime offer ownership leases, observer access and user-authorized takeover as separate operations? Can observers subscribe without taking an exclusive attach slot or changing the operator's grid?
- Can an attach include an initial full-screen snapshot (cursor, scrollback, terminal modes), current geometry and a replay cursor for late joiners?
- Will every supported OS provide the same byte stream, grid updates, cursor state, resize semantics, scrollback access and output acknowledgement and backpressure?
- Can the runtime report bracketed-paste and other terminal modes, cursor position, redraw completion and geometry changes as structured signals?
- Can pane-history and screen reads (read, search, scroll) be side-effect-free, isolated from interactive state so they cannot scroll or block an attached TUI, and guarded atomically by a revision?

**Input**
- What are the delivery guarantees for input and output: ordering, acknowledgement, duplicate handling, and final output before exit?
- Can the runtime check pane identity and write input atomically, including session and process identity and current authorization?

**Prompts, status and conversation**
- Can prompts and approvals be exposed as structured, versioned requests for every supported agent, with prompt IDs, choices, liveness, stale-request detection and a typed answer operation?
- Which event contract distinguishes working, idle, blocked, done and background-wait states, including turns started by runtime messages rather than user prompts, and including input readiness?
- What is the canonical agent, session and conversation identity model? Does it hold across launcher changes, child processes, brand aliases, resumes, branches and agents the built-in catalog does not know?
- Can conversation history be a single structured model of typed records with stable call IDs, turn boundaries, branch and rewind markers, metadata and pagination cursors, or must per-agent transcript adapters remain?
- Which screen-derived behaviors must stay as compatibility fallbacks, and which can be removed once structured signals exist?

**Machines, workspaces, plugins and updates**
- Can remote machines connect to a first-class agent-native endpoint without SSH-installed bridge bundles? How are credentials scoped and rotated?
- Which workspace, worktree, plugin and update capabilities belong to the runtime, and which belong to Ovis's orchestration layer?
- Must the runtime keep herdr's workspace, tab and pane semantics, including focus and close-group behavior?
- Can plugin invocations, like prompt requests, have structured IDs, state transitions and a durable result lookup?
