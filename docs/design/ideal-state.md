# ovis-terminal ideal state

ovis-terminal is a new product, starting from a repository without a runtime implementation: an agent-native terminal runtime that replaces herdr underneath Ovis, not a fork of herdr's TUI or a replacement for the Ovis client. Ovis (`devswha/ovis`, Bun + React) remains the phone and browser interface. This document defines the full destination, not a staged subset or a claim about functionality already implemented.

Evidence references resolve to [the herdr/herdr-core catalog](../research/herdr-catalog.md) (`CAT-`), [Ovis consumer needs](../research/ovis-consumer-needs.md) (`NEED-`), and [isolated runtime observations](../../../../../../tmp/ulw-ovis-yCJzPH/evidence/smoke/runtime-observations.md) (`RT-HC-` and `RT-HD-`). The accompanying `/tmp/ulw-ovis-yCJzPH/evidence/smoke/bridge-traps-map.md` distinguishes reproduced runtime behavior from Ovis policy and platform behavior not exercised on Linux. The headers of both `evidence/g3/mech-scan-herdr*.md` reports were inspected for scope; their scan categories alone do not establish runtime defects. Evidence motivates the proposed contracts below; it does not imply that either existing runtime already meets them.

## Affected users

### Coding agents

Today coding agents use herdr's CLI and socket API or hc's headless commands to launch, address, read, send to, and wait for terminals. Herdr can silently answer a process query for the focused pane or split that pane when the caller supplied an unrecognized target field, so an apparently successful operation can affect unrelated work (RT-HD-02, RT-HD-03). Hc supplies declared OSC 7501 status, parent/child relationships, and structured errors, but its observed send latency, output-wait race, and unproven interrupt result make orchestration harder than the command names suggest (CAT-3122, CAT-3139, RT-HC-01, RT-HC-02, RT-HC-03). Afterward agents address stable resources through the same discoverable, typed API locally and remotely, without opening a TUI or borrowing human focus. Sending returns a delivery receipt independently of a later turn wait, and waits consume explicit status, process exit, or output cursors rather than timing guesses. Agents of any brand can register sessions, prompts, conversations, and children, while missing reports remain explicitly absent instead of becoming fabricated idle or done states.

### Ovis client

Today Ovis is a Bun + React consumer of herdr that connects phones and browsers to local and remote terminals. Its server opens a socket per RPC, reconstructs state across subscription gaps, and parses attach diagnostics and ANSI output to decide whether input is ready (NEED-018, NEED-043, NEED-095, NEED-096). It also owns workarounds for provider-specific prompts and transcripts, Windows mirroring, output credit, geometry leadership, and authority checks that the runtime does not expose as one coherent contract (NEED-074, NEED-089, NEED-103, NEED-141). Afterward Ovis connects to ovis-terminal through a versioned endpoint with multiplexed RPC, events, terminal channels, and explicit role negotiation. Snapshot boundaries, attach readiness, prompt versions, conversation branches, and mutation receipts let the client render authoritative data without inferring lifecycle facts from presentation. Ovis continues to own navigation, chat presentation, notification policy, and phone/browser interaction, while the runtime owns PTYs, terminal state, resource identity, authorization enforcement, and recovery.

### Human at the terminal

Today a human uses herdr's multiplexer chrome and attach client, or hc's interactive attach, alongside programs controlled by other clients. Shared focus, takeover, read-induced scrolling, and viewport-driven resizing can change what that human sees or receives without a deliberate local action (NEED-050, NEED-056, NEED-158, RT-HD-07). The live smoke also showed a successful explicit status report being replaced by a screen guess, so a displayed state can disagree with the agent that reported it (RT-HD-09). Afterward the human's terminal is a first-class client of the same runtime, with an explicit input and geometry lease and independently selectable views. Phone observation, agent queries, and structural mutations do not steal that lease, scroll the application, or move the human's focus. A deliberate takeover identifies the displaced owner, completion remains a factual turn outcome rather than an unseen badge, and disconnection retains uncertain input as a draft instead of replaying it.

### Remote machines

Today a remote machine hosts herdr or hc behind machine-specific sockets and SSH transports, with different platform capabilities and lifecycle rules. Ovis installs and supervises bridges, checks runtime and bridge identity separately, and compensates for Windows attach and process-inspection differences (NEED-014, NEED-085, NEED-114, NEED-154, NEED-155). Hc already demonstrates byte-transparent transport and PTY holders that separate program lifetime from the control server, but these designs do not by themselves give every remote caller scoped authority or complete recovery evidence (CAT-3666, CAT-3070, NEED-167). Afterward each machine exposes an authenticated runtime identity, negotiated capabilities, stable resource addresses, and bounded operations through a persistent transport. A lost line marks that machine unavailable without routing work locally, omitting its resources, killing its PTYs, or freezing other machines. Restart, host reboot, credential renewal, orphan handling, and staged updates have distinct observable outcomes, so Ovis and agents can recover without interpreting shell banners or assuming old processes survived.

## Design principles

1. **Make the runtime a headless service with equally capable agent and Ovis interfaces.** This keeps PTY ownership and structured operations independent of herdr's presentation layer and Ovis's phone/browser layout (CAT-3070, NEED-017, NEED-165).
2. **Require explicit stable identity and validate every operation against its declared target.** This prevents focus, pane moves, PID reuse, and ignored parameters from redirecting a valid-looking request (NEED-099, RT-HD-02, RT-HD-03).
3. **Keep connections persistent and multiplex independently cancellable operations and streams.** This removes per-call connection churn without allowing a second subscription or a slow call to interrupt existing delivery (CAT-3166, RT-HD-01, RT-HD-08).
4. **Give snapshots, events, and replay a shared revision boundary with explicit loss.** This makes reconciliation deterministic rather than dependent on which socket or poll happened to finish first (CAT-3221, NEED-031, NEED-044).
5. **Treat declared agent state as authoritative and absence of a report as absence of knowledge.** This allows unknown brands and parent agents to remain coherent without a screen heuristic overwriting their reports (CAT-3690, RT-HD-09, RT-HD-10).
6. **Separate admission, PTY delivery, agent acceptance, turn completion, and process exit.** This prevents a send or interrupt receipt from making claims it cannot prove and removes sleep-based send/wait synchronization (RT-HC-01, RT-HC-02, RT-HC-03).
7. **Preserve human control through explicit leases rather than implicit focus or takeover.** This lets observation and automation coexist with an operator without resizing or displacing their terminal (NEED-056, NEED-158, NEED-168).
8. **Bound memory and work per consumer while keeping control traffic independently serviceable.** This prevents one slow phone, unread stream, or unavailable machine from stalling other terminals and cancellation (CAT-3181, NEED-036, NEED-074).
9. **Expose prompts and conversations as versioned domain records rather than terminal-screen interpretations.** This gives Ovis reliable answers, histories, branches, and completion alerts across agent implementations (NEED-107, NEED-130, NEED-146).
10. **Separate program survival, durable metadata recovery, and transport reconnection.** This avoids claiming a restored layout proves a process survived and keeps server replacement from destroying unrelated work (CAT-3070, NEED-097, RT-HD-05).
11. **Enforce caller authority inside the runtime at the moment of mutation.** This makes observe roles, prompt answers, and remote machine scopes effective even when a client is buggy or its authorization changed after connection (NEED-099, NEED-164, NEED-167).
12. **Make every supported behavior discoverable, structured, and observable without side effects.** This lets callers branch on schemas and error kinds rather than terminal prose, hidden flags, or a status query that starts a daemon (CAT-3109, CAT-3106, RT-HC-04).

## Kept herdr and herdr-core designs

Keep these mechanisms or contract ideas, not every implementation detail attached to them in the existing products.

- **Negotiated hello:** retain generation, version, identity, methods, and capability discovery rather than platform guessing (CAT-3195).
- **Breaking-change generation gate:** reject an incompatible generation before acting (CAT-3190).
- **Framed wire protocol:** retain the small documented nine-byte channel/kind/length header and separation of control JSON from terminal bytes (CAT-3166).
- **Per-stream credit:** retain bounded, consumer-specific output flow control, with explicit gap/checkpoint recovery rather than silent replacement of bytes (CAT-3170).
- **Control-first scheduling:** keep cancellation, replies, input control, and healthy streams independent of a stalled viewer (CAT-3181).
- **OSC 7501 status:** retain program-declared state, kind, progress, application, title, and message without translating a brand into a guessed lifecycle (CAT-3122).
- **Hierarchical status records:** retain root and child records with explicit replace and clear operations (CAT-3126).
- **Turn counters:** retain a monotonic generation for transitions, while distinguishing blocked or interrupted transitions from successful completion (CAT-3125).
- **No screen inference:** adopt the explicit refusal to infer agent identity or status from terminal presentation (CAT-3690).
- **Typed event envelope:** retain event type, target, data, and sequence as machine-readable fields (CAT-3047).
- **Global sequence within a lifetime:** retain a shared snapshot/event ordering boundary, scoped by runtime identity (CAT-3052).
- **Snapshot, heartbeat, and missed:** retain initial snapshot plus ordered delivery, heartbeat, and explicit loss recovery, consistently across transports (CAT-3221).
- **Pinned subscription cursor:** retain the principle of capturing the observation boundary before setup probes (CAT-084).
- **Initially satisfied waits:** retain immediate satisfaction when a newly installed filter already matches current state (CAT-107).
- **PTY holder separation:** retain program ownership outside the replaceable control server so clients and server restarts do not own program lifetime (CAT-3070).
- **Crash supervision:** retain automatic recovery of the control plane without relaunching surviving programs or hiding recovery state (CAT-3071).
- **Planned restart distinct from stop:** retain program-preserving restart as an explicit operation, with platform-equivalent behavior rather than relying solely on Unix signals (CAT-3120).
- **Logout-independent service lifetime:** retain the Linux service-model objective and provide equivalent guarantees on every supported platform (CAT-3377).
- **Declared parent/child agents:** retain parent links, notification preferences, child retention, and explicit die-with-parent policy (CAT-3139).
- **Remote orphan propagation:** retain queued parent-death communication across a disconnected machine link (CAT-3427).
- **Remote deadlines and cancellation:** retain bounded cross-machine calls and cancellation propagation with explicit commit outcomes (CAT-3428).
- **Template discovery:** retain named role templates with descriptions, extended by schema and version metadata (CAT-3199).
- **One structured run operation:** retain launching direct argv or a template through the same API (CAT-3198).
- **Readiness-bound first message:** retain holding a task until declared readiness, excluding output silence as proof of readiness (CAT-3131).
- **Send-to-turn correlation:** retain the relationship between a send receipt and a subsequent wait, without the observed output-wait registration race (CAT-3210).
- **Reason-bearing waits:** retain explicit state, exit, loss, and timeout results rather than output-silence completion (CAT-3211).
- **Read-only observation from a pipe:** retain machine-usable viewing that does not require a TTY or input ownership (CAT-3034).
- **Uniform machine/resource addresses:** retain local and remote addressing through the same model, resolving aliases to stable identities (CAT-3028).
- **Opaque terminal IDs:** retain runtime-owned identity independent of layout position or display labels (CAT-2255).
- **Atomic submissions:** retain non-interleaving text and commit delivery across concurrent writers (CAT-1903).
- **Versioned `doc.get`:** retain named opaque documents with explicit value and version, including the absent-document result (CAT-3228).
- **Compare-and-swap `doc.set`:** retain optimistic concurrency, bounded values, atomic persistence, and conflict hints (CAT-3229, CAT-3220).
- **Document change events:** retain name/version notifications that let subscribers refetch authoritative values (CAT-3231).
- **Atomic fsync and replacement:** retain durable state commits that never expose a partially written snapshot (CAT-1639).
- **Corrupt-state quarantine:** retain recovery copies, but expose the corruption and lost state rather than silently treating an empty store as intact (CAT-3481).
- **Byte-transparent custom transport:** retain the small transport contract of unchanged bytes and no interactive prompting on the protocol channel (CAT-3666).
- **Structured error kinds plus hints:** retain stable error classification separate from explanatory prose (CAT-3106).
- **Published exit codes:** retain distinct machine-usable CLI outcomes for usage, missing targets, unavailable services, blocked operations, and cancellation (CAT-3107).
- **Clean CLI channels:** retain JSON success on stdout and structured failure on stderr, with explicit JSON mode independent of TTY detection (CAT-581).
- **Discoverable OpenRPC schema:** retain a machine-readable method, parameter, result, and error catalog suitable for generated Ovis types (CAT-3109).
- **Released-schema compatibility gate:** retain checks against removed methods, newly required inputs, narrowed accepted values, and lost required outputs (CAT-3471, CAT-3472).
- **Embedded `hc --skill` design:** ship the equivalent version-matched agent manual inside the ovis-terminal binary and keep it discoverable from help (CAT-3316).

## Assumptions

- **Not reversible within this definition - product boundary:** ovis-terminal is a new agent-native runtime replacing herdr underneath Ovis; Ovis remains the Bun + React phone/browser client, and this document describes the full destination rather than an MVP.
- **Reversible - implementation stack:** Bun/TypeScript is recommended because the host has Bun 1.4 with native PTY support through `Bun.spawn({ terminal })` and single-binary packaging through `bun build --compile`, while no Rust toolchain is installed; the stack decision remains open, and Rust is an alternative if measured PTY, emulator, recovery, portability, or packaging requirements justify it.
- **Reversible - platform backend:** Linux, macOS, and Windows are full target platforms with the same observable runtime contracts; native Bun PTY availability on this workstation is not evidence of complete Windows support, and platform adapters or a separately built native holder may be required without reducing those contracts.
- **Reversible - terminal emulator and holder implementation:** the runtime owns terminal parsing, screen checkpoints, modes, and scrollback, but no particular emulator library, process-supervision library, or native binding is selected here.
- **Reversible - protocol form:** use an hc-inspired framed persistent connection with JSON-RPC control, separate stream channels, explicit generation negotiation, and a browser-compatible authenticated transport adapter; exact method spelling and transport bindings remain design choices, but multiplexing and typed outcomes do not.
- **Reversible - legacy compatibility:** the needs document's one-request and close-after-response rules describe Ovis's current adapter behavior, not the new product's destination; NEED-003 and NEED-007 are superseded by persistent connection and per-request settlement contracts, and any legacy adapter must not impose herdr's socket lifecycle on native clients.
- **Reversible - latency acceptance profile:** the proposed 100 ms local send-admission and committed-event delivery bounds apply to a healthy local runtime on the stated workstation, with at most 16 live PTYs, eight connected clients, 16 simultaneous control requests, and 1 MiB/s aggregate terminal output, using writable local sockets; measurement excludes OS suspension and network transit, and production overload must return typed backpressure rather than accept unbounded work.
- **Reversible - deadlines and resource defaults:** ordinary calls default to 10-second caller-visible deadlines, idle subscriptions to 15-second heartbeats, and frames to a 16 MiB ceiling; event replay retains up to 10,000 events or 64 MiB, whichever limit is reached first, while negotiated pagination supports larger logical results and advertises every retention floor.
- **Reversible - delivery and receipt model:** events are replayable and deduplicated by lifetime/sequence, not claimed to be exactly-once across arbitrary crashes; mutation receipts default to a durable 24-hour deduplication window, and missing or expired outcome evidence produces an explicit unknown/expired result rather than automatic resend.
- **Reversible - ownership model:** multiple viewers share a terminal while one explicit controller lease governs input and one eligible interact lease governs geometry; authorized agent submissions use the same sequencer and do not acquire authority from window focus or a silence timer.
- **Reversible - agent integration boundary:** explicit registration, OSC 7501, and typed provider adapters supply lifecycle, prompts, and conversation records; adapters may parse authorized native stores with provenance, but terminal-screen guesses never become authoritative state and unintegrated programs remain usable terminals with unavailable structured features.
- **Reversible - runtime versus client services:** runtime scope includes workspace/worktree state, template launch, plugin run lifecycle, versioned documents, and staged update operations, while Ovis owns presentation, notification policy, and approval UX; execution permissions remain enforced by the runtime regardless of which client renders them.
- **Not reversible within this definition - uncertainty and authority:** missing process evidence is not proof of exit, a PTY write is not agent acceptance, an observer is not a controller, and a restart is not proof that every prior program survived.
- **Not reversible within this definition - trust decisions:** host-key acceptance, credential entry, takeover, and destructive group scope remain explicit authorized actions represented in structured requests; removing interactive TUI prompts does not authorize the runtime to make those decisions itself.
